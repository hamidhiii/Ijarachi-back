# Changelog

Заметные изменения бэкенда Rentoo. Карта проекта — [PROJECT_OVERVIEW.md](PROJECT_OVERVIEW.md).

## 2026-11-27 — фискальный чек Payme

- `CheckPerformTransaction` (`/api/v1/billing/payme/`) возвращает `detail` для
  чека в налоговую: `receipt_type` 0 и одна позиция — `title` на узбекском
  («Rentoo START tarifi — 1 oy», «Rentoo e'lonni TOPga ko'tarish — 7 kun»,
  «Rentoo VIP e'lon — 30 kun»), `price` в тийинах, `count` 1, `code` (MXIK),
  `package_code`, `vat_percent`. Сумма позиций сверяется с суммой заказа.
- Новые настройки: `PAYME_FISCAL_MXIK`, `PAYME_FISCAL_PACKAGE_CODE`,
  `PAYME_FISCAL_VAT_PERCENT`; для продвижения — `PAYME_FISCAL_MXIK_PROMO` и
  `PAYME_FISCAL_PACKAGE_CODE_PROMO` (пусто — как у тарифа). Без MXIK — предупреждение в логе.
- Порядок подключения Payme на сервере — PROJECT_OVERVIEW.md, §6c.

### Сделка выключена флагом
- `DEAL_FLOW_ENABLED` (по умолчанию `False`): оформление и оплата брони, эскроу,
  залог, кошелёк, споры, торг, комиссия и отзывы по сделке выключены, но не
  удалены. Эндпоинты отвечают 410 `DEAL_FLOW_DISABLED`, задачи Celery по сделкам
  не выполняются. Тестовые настройки держат флаг включённым для тестов сделки.

### Тарифы и лимит объявлений
- Новое приложение `billing`: тарифы FREE / START 99 000 / BUSINESS 199 000 /
  PRO 399 000 сум в месяц, подписка пользователя и история периодов.
- Лимит активных объявлений по тарифу: FREE 10, START 100, BUSINESS 300, PRO без
  лимита. Ошибка — 400 `LIMIT_REACHED` (была `listing_limit`) с полями `plan`,
  `limit`, `active`. Тип «магазин» лимит больше не повышает;
  `LISTING_LIMIT_PRIVATE` / `LISTING_LIMIT_SHOP` удалены.
- `Item.quantity` — количество одинаковых вещей в объявлении (≥ 1); уменьшить
  его ниже уже забронированного на будущие дни нельзя.
- Оплата тарифа разовым платежом за 30 дней: `POST /api/v1/billing/orders/`,
  Payme Merchant API (`/billing/payme/`) и Click SHOP API
  (`/billing/click/prepare|complete/`), заглушка при `PAYMENTS_MODE=stub`.
  Тот же тариф продлевается с конца периода; тариф выше начинается сразу, а
  неиспользованные дни прежнего пересчитываются по цене в дни нового и
  добавляются к сроку; ниже — после окончания.
- По окончании тарифа — FREE: лишние объявления уходят в «неактивные» (не
  удаляются) и возвращаются сами после новой оплаты. Напоминания за 3 дня и в
  последний день (уведомление `billing`).
- Права тарифов проверяет сервер: 403 `PLAN_FEATURE_REQUIRED`.
- Продвижение: «Поднять в топ» 30 000 сум на 7 дней и VIP 80 000 сум на 30
  дней, тем же заказом; в карточках `is_top` / `is_vip`. Выдача по умолчанию:
  VIP > топ > приоритет BUSINESS/PRO > дата.

## блок 2: важные исправления из обзора кода

Ветка `fix/block-2` (поверх блока 1). Интеграции Click/Payme/MyID не входят.

### Безопасность
- **OTP:** код генерируется через `secrets`; после `OTP_MAX_ATTEMPTS` (5)
  неверных вводов живые коды номера гаснут — подбор шести цифр больше не упирается
  только в ограничение частоты. То же для смены телефона. Ответы различаются
  кодами `otp_invalid` / `otp_attempts_exceeded`.
- **Заблокированный пользователь:** вход по OTP — 403 `user_blocked`; обновление
  токена — 401; WebSocket не подключается; при блокировке отзываются все его
  refresh-токены.
- **Модерация:** правка названия, описания, категории, характеристик или адреса
  одобренного объявления и новое фото возвращают его на модерацию. Цена и залог
  при правке тоже проверяются (> 0 и ≥ 0).
- **Телефоны в чате** видны только после раскрытия контактов по сделке; в
  переписке до брони — только свой номер.
- **Web Push:** подписка только на HTTPS-адреса известных push-сервисов
  (`WEB_PUSH_ALLOWED_HOSTS`) — закрыт SSRF через endpoint подписки.
- **Прод-конфиг:** без своего `SECRET_KEY` в `APP_ENV=prod` сервер не стартует;
  порт 8000 в docker-compose — только `127.0.0.1`.

### Цена и торг
- **Комиссия по модели B:** арендатор платит цену владельца + залог, комиссия
  (по умолчанию теперь **15 %**) удерживается из выплаты владельцу; выплата
  считается по комиссии, зафиксированной в сделке. В превью и карточке сделки —
  `owner_payout`; для формы объявления — `GET /api/v1/pricing/payout/`.
- **Принятый торг меняет цену сделки:** сделка считается от согласованной цены и
  хранит ссылку `offer`. Сумма предложения и встречного — > 0; в ветке одна
  ставка без ответа (`offer_pending_exists`).
- **Даты брони:** начало не в прошлом, срок не короче `min_rental_days`.

### Прочее
- Сообщение в чужой диалог — 404 вместо 500.
- Миграции: `users 0008` (счётчик попыток), `bookings 0013` (`Booking.offer`).
- 41 новый тест (всего 98).

## [Unreleased] — блок 1: критичные исправления

Ветка `fix/block-1-critical`. Интеграции Click/Payme/MyID в этот блок не входят.

### Безопасность
- **Telegram-бот:** номер привязывается к чату только если контакт — самого
  отправителя (`contact.user_id == from.id`). Раньше контакт без `user_id`
  (из записной книжки или от стороннего клиента) проходил, и OTP для входа в
  чужой аккаунт уходил тому, кто его прислал. Такой контакт теперь отклоняется
  с просьбой поделиться своим номером кнопкой.
- **Заглушки только вне прода:** новые `APP_ENV` (dev/staging/prod),
  `PAYMENTS_MODE` (off/stub/live) и `MYID_MODE` (off/stub). При `stub` в prod
  сервер не стартует (`ImproperlyConfigured`); сама заглушка ещё раз проверяет
  режим перед подтверждением.
- **Вебхуки Click и Payme** отвечают 404, пока `PAYMENTS_MODE` не `live`.

### Оплата
- Единый интерфейс провайдера оплаты (`apps/payments/providers.py`): наличные,
  Click, Payme, заглушка. При `PAYMENTS_MODE=off` онлайн-оплата — 503
  `PAYMENT_METHOD_UNAVAILABLE`, наличные работают.
- `StubProvider` (dev/staging): платёж `provider=stub` подтверждается сразу; в
  GMV админ-дашборда такие платежи не входят.
- Заглушка MyID: `POST /api/v1/kyc/myid/stub/verify/` (только `MYID_MODE=stub`
  в dev/staging, иначе 404).
- Повторный `POST /deals/{id}/pay/` больше не получает 409 из-за собственных
  дат сделки; прежние незавершённые попытки оплаты помечаются `failed`.
- Оплата, пришедшая за уже отменённую сделку, не возвращает её в `paid`.
- **Владелец подтверждает бронь вручную** (`pending_payment → confirmed`)
  **только при оплате наличными**; онлайн-оплату подтверждает провайдер.

### Даты
- Занятость дат считается по активным броням (`pending_payment`, `paid`,
  `in_progress`), а не по общему списку `blocked_dates`. Отмена или истечение
  брони освобождает только её дни — раньше отмена черновика или просроченной
  заявки стирала и даты чужой оплаченной брони.
- Проверка пересечения и занятие дат — в одной транзакции под
  `select_for_update` объявления: две одновременные оплаты одних дат больше не
  проходят обе.
- `ItemAvailability.blocked_dates` — только ручные блокировки владельца; PATCH
  календаря не может освободить дни броней. `GET .../availability/` добавил
  поля `manual_blocked_dates` и `booked_dates`.
- Аренда не длиннее `BOOKING_MAX_DAYS` (365 дней).

### Залог и кошелёк
- Залог: `Booking.deposit_status` и история `DepositOperation`, оба в карточке
  сделки. При завершении сделки залог возвращается арендатору в кошелёк; по
  спору сотрудник удерживает часть или весь залог в пользу владельца —
  `POST /deals/{id}/resolve-dispute/`. Раньше залог не возвращался никогда.
- Кошелёк: новая модель `WalletTransaction` (тип, сумма, сделка, баланс после,
  дата). Начисления только через `credit_wallet`: `select_for_update` + `F()`.
  Параллельные `release_escrow` не теряют и не дублируют начисления
  (блокировка сделки + уникальное ограничение на начисление по сделке).
  `release_escrow` запускается после коммита.
- В админке баланс, журнал кошелька и история залога — только для чтения.

### Миграции
- `bookings 0011–0012`, `catalog 0011–0012`, `payments 0006`. Данные: у
  существующих сделок проставлен `deposit_status`; у уже рассчитанных сделок с
  залогом он `held` — **эти залоги не были возвращены и требуют ручного
  возврата**. Из ручного календаря убраны дни, покрытые бронями.

  `python manage.py test --settings=core.settings_test` (нужен PostgreSQL).
